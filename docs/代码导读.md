## 二、4 条主链路（面试就讲这四条）

### 链路 1：上传简历 → 拿到文本
`analyze/page.tsx` 把文件 FormData POST 到 `/api/resume` → 路由按扩展名分支：`.txt/.md` 直接解码，`.pdf` 走 `unpdf` 的 `getDocumentProxy + extractText` → 归一化空白 → 返回 `{ text, pages, chars, kind }`。
**关键点**：全程在内存里，不落盘；< 80 字判定为扫描件并返回 422。

### 链路 2：算分（最核心）
`matchResumeToJd(resumeText, jd)`：
1. `splitResume` 按「专业技能 / 项目经历 / 教育背景」等小标题分段（启发式，失败退化为全文）；
2. 对 JD 每个技能 `gradeEvidence`：在项目段命中且带量化单位 → level 3；只在项目段 → 2；只在技能清单 → 1；没有 → 0；
3. 加权：`score = Σ(weight × must?1.5:1 × level/3) / Σ(weight × must?1.5:1) × 100`；
4. 输出四档分组 + 每条证据的原文片段（以技能词为中心截取，避免四张卡引用同一句话）。

### 链路 3：流式建议
`advice-panel.tsx` → `streamText()` 读流 → `/api/advise`：先用 zod 校验「简历 + JD」，**服务端重新算报告**（不接受客户端分数），无 Key 直接返回规则版文本；有 Key 则 `streamChat()` 手写解析 SSE 并逐块 enqueue。

### 链路 4：守卫
`guard(req, { scope, limit })` 在每个接口第一行：先比对 `x-access-token`（`timingSafeEqual`），再按 `IP+接口` 计数，超限返回 429 + `retry-after`。

## 三、3 个算法细节（面试加分项）

**① 词表匹配为什么要"长词优先 + 单词边界"**
直接 `includes("go")` 会命中 `django`、`includes("ts")` 会命中 `artifacts`。做法：别名按长度倒序，拉丁词加 `(?<![a-z0-9])…(?![a-z0-9])` 边界断言；中文按子串匹配。词表构建期还会检查别名冲突（同一别名指向两个技能直接抛错）。

**② 证据分级为什么不用 LLM**
LLM 同一输入两次可能给两个分，用户没法验证、面试官没法追问。规则版可复现、可解释、可写单测；LLM 只负责把结论讲成人话（且加"禁止编造数字、举例用占位符"的硬约束）。

**③ 量化识别为什么用"单位白名单"**
"5 张数据表""3 处索引""2800 行"这类中文结果，光看数字无法判断是不是量化。做法：`数字 + 单位` 才算，单位表从真实简历里长出来（张/组/行/页/处/项/条/%/ms…），少一个单位就会把实打实的结果误判成"没量化"——这是被测试抓出来的真实 bug。

## 四、面试怎么说（三句话模板）

1. **一句话定位**：「一个把简历和 JD 逐条对照、按证据强度打分的工具，分数可复现、可解释。」
2. **一句话技术**：「规则引擎打分 + 服务端重算 + 手写 SSE 流式，LLM 只做润色，无 Key 自动回退规则版。」
3. **一句话证据**：「26 条 pytest 接口用例 + 11 条引擎断言 + GitHub Actions 门禁，首轮 E2E 抓出 4 个真实缺陷并修复。」
